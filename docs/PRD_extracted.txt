OMNIX: Product Requirements Document (v0.5 draft)
Updated 16 November 2026 (Web Application architecture pivot, Core Pipeline specification, and Moodle deferral) for the IIT Madras / Commonwealth of Learning (COL) Training of Trainers programme. Status: draft for team review.
1. Summary
OMNIX (Open Multimodal Network for Immersive eXperiences) is a server-hosted web application (React frontend + FastAPI backend) accessible by educators via standard web browsers. It requires zero client-side installation on educator laptops, letting teachers turn a chapter (a PDF, document or typed topic) into classroom-ready material: images and diagrams, slide decks, narrated explainer videos, games, simulations, 3D/AR objects and comics. It does this behind one simple web interface, by stitching existing open-source tools and hosted model APIs instead of building a custom AI framework.
Product goal. After a three-day ToT, each trainer can independently produce a chapter-level learning package and train other educators to do the same.
Design principles
The LLM never writes free-form programs for production paths. It fills JSON schemas and templates, and deterministic renderers produce the output.
Models never draw text. Labels and captions are rendered by layout code.
Simulations are selected from a catalogue, never generated.
Every output ships with its source data so a trainer can verify accuracy before approving.
Every provider sits behind a capability interface and can be swapped in config.
Stitch and vendor existing repos; write only the thin core ourselves.
Added in v0.5:
Architectural pivot to Web Application: zero OS-specific installers or client-side runtime requirements; trainers access OMNIX via browser (Chrome, Edge, Safari) on any laptop or tablet. Server-side backend (Linux/Docker) manages ffmpeg, LaTeX, and Kokoro ONNX.
Core pipeline prioritized: End-to-end ingestion (pypdf/python-docx), Groq-powered outline, python-pptx slides, client-side Mermaid diagrams, Parallel Storyboard Manim video with kokoro-onnx audio-first sync and 480p Draft Mode, and deterministic passage grounding. Moodle depth (.mbz, LTI) is deferred for future discussion; packages export as self-contained offline classroom bundles with an index.html viewer.
2. Background and source requirements
The COL/IIT Madras curriculum defines a 3-day, 15-hour programme: Day 1 visuals and presentations, Day 2 3D, games, simulations and XR, Day 3 animation, video and comics. Trainers are taught what each capability can do and how to prompt OMNIX; they are not taught production software. The curriculum states a central principle: teach creative possibilities and educational value, and let OMNIX handle production complexity. It also says the programme must not promise functionality that is not implemented, so everything demonstrated must work live.
3. Users and key scenarios
Primary user: an educator or master trainer with a standard laptop, tablet or desktop and a modern web browser; not a developer. Zero client-side software installation required.
Core scenario (chapter-first). The trainer creates a Chapter project, adds a PDF or document (or types a topic), sets subject and grade, reviews the generated chapter outline, then generates slides, an explainer video, a game, a simulation pick, an image and optionally a 3D object or comic. They review each output beside its source data, approve or reprompt, and export a learning package.
Secondary scenarios: one-off generation (for example just an image); saving and reopening a project; exporting an offline classroom package; trainers demonstrating one capability to other educators.
4. Scope
In scope (January delivery): the core pipeline tool families in section 5, document upload, project save/reopen, approve-or-reprompt review, offline classroom package export, first-run setup wizard, English language.
Out of scope for January: OS-specific desktop installers, local LaTeX/ffmpeg client setup, lecture recording, link/URL ingestion, in-app WYSIWYG editors for slides/video, Moodle .mbz/LTI integration (deferred for future discussion), VR headset experiences, non-English UI, T2V as a required deliverable.
Stretch: editing source data through auto-generated forms; Moodle LTI link; additional narration languages; masked image editing.
Delivery tiers (v0.5). Tier 1, fully integrated core pipeline: chapter project, lightweight ingestion, outline, slides, diagrams and mindmaps, images, Parallel Storyboard Manim video (with Draft Mode), I2V clips, H5P quiz/flashcards, PhET picker, grounded review gate, and offline package export. Tier 2, minimal UI viewer stubs: 3D/AR (model-viewer) and comics. Deferred: Moodle depth, T2V polish, html_video, Docling neural scan pack.
5. Functional requirements
Priority: P0 must work at the ToT, P1 should, P2 stretch.
Acceptance criteria (selected)
F5: output opens and edits cleanly in PowerPoint and LibreOffice; no text clipped; every slide traces to outline items.
F6: a 5-minute video renders as independent scenes using verified templates; draft mode preview renders each scene in <30 seconds on CPU; kokoro-onnx TTS audio duration dynamically drives scene pause time (self.wait); a failed scene retries once with fallback template parameters; total render time is shown before starting.
F8: generated .h5p validates and plays; correct answers match the source data panel.
F9: the selected sim URL exists in the catalogue (never LLM-invented) and loads.
F12: a trainer can see why a generation failed and what to change.
F16: clips can be drafted concurrently in low-res Draft Mode; educators can review and reorder scene cards on a visual storyboard; final MP4 assembly joins all approved clips in order with synchronized narration and captions.
F17: on the golden chapter, at least 95 percent of quiz answers and slide facts carry a source reference that matches the chapter text.
6. Non-functional requirements
Reliability: golden-prompt suite for each P0 tool, run by omnix check; target at least 90 percent pass on the demo prompt set (defaults accepted 16 November).
Latency: progress visible within 5 seconds of starting a job; long-job ETAs shown.
Platforms: Universal web browser support (Chrome, Edge, Firefox, Safari). Zero client-side software installation. Server backend runs on standard Linux (Docker container / Ubuntu VM) with pre-installed ffmpeg, Cairo/Pango, TeX Live, and kokoro-onnx.
Offline & Venue Resilience: For offline or air-gapped venues, the server backend runs on a local workshop host machine over local Wi-Fi/LAN, with pre-cached 'Golden Chapter' packages (Grade 9 Physics, Grade 10 Biology) built into the app for fail-safe live demonstrations.
Security and privacy: keys stored locally (OS keychain or .env), never logged; the local server listens on 127.0.0.1 only and requires a per-session token; free-tier providers may log prompts, which is acceptable per the team, and trainers are told so.
Accessibility: captions on videos; alt text on generated images; readable contrast in templates.
Licensing: only OSI-approved licences for bundled code; no GPL/AGPL code copied into the core (see section 9).
Maintainability: each tool is a folder with a manifest and smoke test; no tool imports another tool.
Targets (accepted defaults, to be benchmarked in M0). Tier 1 tools pass at least 90 percent of about 20 golden prompts. Groq outline within 15 seconds, diagram or image within 30 seconds, slides within 45 seconds, quiz within 20 seconds. A Draft Mode preview for a Manim clip renders within 30 seconds (480p/15fps); final high-definition clip (1080p) renders within 2–3 minutes on server CPU. An I2V clip returns within 5 minutes (provider dependent). Progress shows within 2 seconds of starting a job, and no work is lost on a restart.
7. Architecture
Layers
UI: a modern React, TypeScript, Vite and Tailwind web application. Schema-driven forms are rendered dynamically from Pydantic schemas via FastAPI endpoints (/api/tools/{name}/schema), eliminating the need for hand-crafted per-tool form components. The UI consists of four focused views: Chapter Dashboard, Schema Form Modal, Generic Artifact Card, and a Storyboard Clip Review Grid.
Core (own code, small): tool registry, brief schemas (Pydantic), job runner (FastAPI plus SQLite worker), config, project and package format, review gate.
Tools: one folder per capability with tool.yaml, run(brief, ctx) -> Artifact, and a smoke test.
Provider layer: capability interfaces llm, image, video, tts, 3d; adapters per provider; config chooses and orders providers with automatic failover.
Storage: project folders on disk. Each artifact is files plus manifest.json holding type, source data (script, quiz answers, captions), provider and model versions, cost and licences.
Tool contract. Every tool takes a validated brief (topic, level, purpose, output, constraints, chapter outline reference) and returns an Artifact. Tools never read keys or call providers directly; they use ctx.llm, ctx.image, ctx.video, ctx.tts.
Provider interfaces. Adapters declare capabilities (allowed durations, resolutions, sizes) and the core clamps or translates requests. Adapters hide async job polling, download results immediately, map errors to RateLimited, QuotaExhausted, BadInput and ProviderDown, and report estimated cost.
Isolation. Start with one Python environment. A tool may declare runtime: venv or container in its manifest only if dependencies conflict. Heavy model code (Wan, TRELLIS) never runs on trainer laptops; it is reached through hosted APIs.
Pipeline pattern for every tool: brief, plan (LLM returns JSON), validate (schema plus sanity checks, one retry), render (deterministic), review (trainer approves or reprompts).
Manim video pipeline. Chapter outline, storyboard of scenes (JSON), per-scene template selection and parameters from a verified STEM component registry. Free-form code-generation fallback is eliminated from production paths to guarantee zero compiler crashes during live demos. Dynamic AV synchronization: kokoro-onnx TTS audio is generated first per scene; audio duration dynamically sets the Manim scene duration and pause length (self.wait(max(0.5, audio_duration - animation_runtime))). Bounding box and coordinate safety margins prevent text and formula overlap. Universal Draft Mode compiles at 480p/15fps for rapid educator review (<30s); final batch compiles at 1080p. Biological anatomy and organic cellular structures are routed away from Manim to 2D image overlays (F4) or 3D models (F10).
Diagram pipeline. LLM writes Mermaid/markmap text, which is rendered 100% client-side in the browser via JavaScript DOM (SVG/Canvas). Zero server-side browser or headless CLI dependencies. Errors are fed back once for repair.
Deployment (decided 16 November)
Deployment (decided 16 November, v0.5): Web Application deployment. The backend is a standard containerized Linux service (FastAPI + SQLite job queue + ffmpeg + TeX Live) deployed on a campus server, cloud VM, or local workshop host machine. Educators connect over HTTP/HTTPS from their existing web browsers without installing Python, LaTeX, or ffmpeg. Server-side job queue regulates concurrent Manim renders (max 3-4 parallel workers) to prevent CPU thrashing. Pre-cached 'Golden Chapter' packages (Grade 9 Physics, Grade 10 Biology) are bundled on the server for fail-safe demonstrations if internet drops.
Provider records and roles
Providers are data, not code. Each record has a kind (openai_compat, litellm, async_job or local), a base URL, a key reference and a model list. One generic OpenAI-compatible adapter covers most LLM hosts and local servers (Ollama, LM Studio, llama.cpp, vLLM) from base URL, key and model alone [verify per provider]. Declarative YAML adapters (submit URL, request template, poll URL, status and result paths) cover async image and video hosts without new code. When a trainer enters a key, OMNIX lists models, runs a JSON-schema test and a tiny image or video test, and records a capability matrix (json, vision, image, i2v, tts). Tools request roles (planner, writer, reviewer, image, i2v, tts) and the trainer assigns a model per role; planner roles refuse models that fail the JSON test. Every adapter reports an estimated cost and maps errors to RateLimited, QuotaExhausted, BadInput and ProviderDown.
Orchestration and routing
The default is explicit: the chapter dashboard has one button per tool. A prompt box suggests a tool: an LLM classifier returns {tool, confidence, brief, reason}, where tool must be an enum from the registry and brief must validate against that tool’s schema (one repair retry). Below a confidence threshold it shows buttons and does not guess. Whole-package requests use plan-then-execute: the LLM drafts ordered steps, the plan is validated against the registry and shown as an editable checklist, and a deterministic runner executes it. Pipeline choice inside video is rule-based (equations, graphs and process diagrams go to Manim; realistic motion and illustration animation go to I2V). Roles in the pipeline: one planner and prompt-refiner LLM (refining is skipped when the prompt is already good), the generators, and an advisory reviewer that only reviews and never generates. There is no free-running agent loop and no multi-agent supervisor graph; a semantic router (embeddings) is optional.
Video project and subject coverage
A video project is a parallel storyboard of clips. Each clip has a mode (manim, i2v or t2v), a brief, a status (draft, generating, needs review, approved), its artifact and optionally a source image. Universal Draft Mode produces low-res (480p/15fps) previews concurrently in under 30 seconds per clip so trainers can review the entire storyboard without waiting. Clips can be reordered or reprompted independently. Final joining, resolution/frame-rate matching, narration and captions are ffmpeg jobs. Hyperframes (Apache-2.0) is an optional later tool for HTML-built animations. Manim is reliable for physics, maths and chemistry diagrams, graphs and process animations; biology anatomy strictly relies on 2D images, SVG overlays and PhET, because Manim procedural vector graphics fail at organic anatomical figures.
Grounding, provenance and versions
Grounding is implemented deterministically without vector database overhead. During lightweight ingestion (pypdf/python-docx), text is chunked into numbered passages stored in passages.json (e.g. P01-S02). Generative prompts require the LLM to output grounding citations alongside each fact, quiz question, and narration line. A deterministic substring/token overlap validator verifies citations against passages.json in <5ms; unsupported items are flagged as “not from your chapter” in the review view. Packages carry attributions, model credits, and an AI-generated label.

13. Risks and mitigations
Slow Manim rendering on laptop CPUs: Draft Mode default (480p/15fps preview in <30s, final 1080p render in background batch), limited parallel scenes, benchmark in M0.
Heterogeneous and locked-down trainer computers: portable embedded Python bundle (pre-bundled ffmpeg/espeak-ng), capability packs, offline bundle, an install session before the event, omnix doctor.
Download and disk size: measure each pack in M0 and keep heavy packs optional.
Frontend workload for two Python-strong developers: schema-driven forms and one generic artifact card instead of per-tool screens.
Venue network: offline readiness check and pre-cached 'Golden Chapter' sample projects (Grade 9 Physics, Grade 10 Biology) bundled locally so trainers can present pre-computed artifacts seamlessly if venue Wi-Fi throttles or API rate limits trigger.
